# Security

This project handles a Spotify refresh token, a GitHub token with write access,
and untrusted text from issue comments and track metadata. That is a small but
real attack surface, so the boundaries are documented rather than implied.

## Reporting

Open a private security advisory:

```text
https://github.com/ajaybe-ops/ajaybe-ops/security/advisories/new
```

Please do not open a public issue for a vulnerability that exposes a token or a
write path. Include the affected file, a minimal reproduction, and the impact.

There is no bounty. There is a fast response and a fix in the default branch.

## Threat model

| asset | who could attack it | worst realistic outcome |
| :--- | :--- | :--- |
| Spotify client secret + refresh token | anyone who can read the Vercel project or the repo | read the owner's currently playing track; no playback control, no password |
| GitHub Actions token | a malicious workflow change | commit to this repository; token is scoped and expires with the job |
| `PROFILE_TOKEN` (optional PAT) | repository admin compromise | read public profile data; classic `read:user` only |
| Issue game state | any GitHub user who can comment | a corrupted or spammed game file, not code execution |
| Rendered SVG | track metadata author | markup injection into the badge if escaping regressed |
| Visitor browser (arcade) | compromised dependency | none: there are no dependencies and no network calls |

Non-goals: this is not a multi-tenant service. It has one owner, one Spotify
account and one repository. There is no user account system, no uploads and no
database.

## Secrets

All secrets live in the hosting provider's encrypted environment store:

| secret | where | scope | exposure |
| :--- | :--- | :--- | :--- |
| `SPOTIFY_CLIENT_ID` | Vercel env | public-ish identifier | never rendered |
| `SPOTIFY_CLIENT_SECRET` | Vercel env | token exchange | server-side only |
| `SPOTIFY_REFRESH_TOKEN` | Vercel env | read playback | server-side only |
| `PROFILE_TOKEN` | GitHub Actions secret | `read:user` | only the stats workflow |
| `GITHUB_TOKEN` | ephemeral, Actions | per-workflow `permissions:` | expires with the job |

Rules enforced by the code:

- The Spotify function never logs request headers, token responses or the
  refresh token. Errors are reduced to categories such as
  `spotify-token-401`.
- The JSON endpoint returns track metadata and a boolean, never a credential and
  never the raw access token.
- The OAuth helper prints the refresh token to the local terminal by design; it
  does not write it to disk. It validates the OAuth `state` parameter and listens
  on `127.0.0.1` only.
- `.env` is ignored. `.env.example` contains empty values.
- No secret is interpolated into an SVG or committed asset.

If a secret does leak, rotate it before investigating how. See the
[rotation runbook](#rotation-runbook).

## Untrusted input

### Issue comments (chess bot)

The bot accepts exactly two shapes:

1. One of six slash commands: `/board`, `/fen`, `/resign`, `/new`, `/reset`,
   `/help`.
2. A single chess move token, parsed by `extractCommand` and validated by the
   engine.

Nothing from a comment reaches a shell, an `eval`, a URL or an HTML sink. The
reply is Markdown containing an ASCII board and text generated by the server. A
comment longer than 400 characters is ignored before parsing. Bot-authored
comments and comments containing the hidden marker are ignored, which closes the
feedback loop.

The bot never trusts the commenter's colour: the engine moves only for
`state.engineColor`, and a visitor cannot submit a move for the engine. State
files are written with the last known blob SHA, so a stale writer cannot silently
overwrite a newer move.

### Track metadata (Spotify SVG)

Track title, artist, album and URL are attacker-influenced (anyone can publish a
track). Everything passes through `escapeXml` before it is placed in the SVG.
The artwork URL is validated against `https://i.scdn.co/`, the content type must
be a raster image, and the payload is capped at 250 KB. The image is inlined as a
data URI; no external reference is emitted.

The response sets:

```text
Content-Type: image/svg+xml; charset=utf-8
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:
```

so even a markup regression cannot load a script or phone home. `check-assets.mjs`
also rejects `<script>` and inline `on*=` handlers in generated SVG.

### GitHub API data (stats)

Repository names, languages and logins are escaped before rendering. Contribution
counts are clamped to sane integers. The renderers emit numbers and escaped
labels, not raw JSON.

## Workflow permissions

Every workflow declares the minimum it needs; none use `write-all`.

| workflow | permissions | why |
| :--- | :--- | :--- |
| `ci.yml` | `contents: read` | checkout and tests |
| `pages.yml` | `contents: read`, `pages: write`, `id-token: write` | build and deploy the static site |
| `profile-assets.yml` | `contents: write` | commit refreshed SVG |
| `chess-bot.yml` | `contents: write`, `issues: write` | commit the game file and comment |

Additional hardening available to you:

- Pin third-party actions to a commit SHA instead of a major tag.
- Restrict Actions to selected actions in organization settings.
- Use a GitHub App or fine-grained token instead of a classic PAT if your
  organization policy prefers it; the script only needs public profile data.
- Enable branch protection so asset refresh commits cannot rewrite unrelated
  files. The workflow stages only the three generated SVGs.

The Actions token is ephemeral. A push made by the token does not recursively
trigger another workflow, which also prevents accidental loops.

## Denial of service and abuse

- **Comment spam** — each issue has a concurrency group; duplicated or racing
  writes fail closed. Comments are capped at 400 characters. The job timeout is
  five minutes. A determined spammer can still consume Actions minutes; if this
  becomes a problem, restrict the bot to issues opened by the repository owner
  (one `if:` in the workflow) or add a label check.
- **Engine cost** — depth is fixed by the workflow, not by the commenter, and the
  engine has no user-supplied search parameters.
- **Spotify function** — tokens and artwork are cached; responses are cached at
  the edge. A 429 from Spotify is handled without retry loops. The function has a
  10-second platform timeout and a bounded artwork download.
- **GitHub API budget** — the stats job makes a handful of REST calls plus one
  GraphQL query every six hours. It paginates at most three pages of repositories.
- **Arcade** — no network calls, no timers that run off-screen (views pause when
  hidden), and reduced-motion support. It cannot be used as a proxy or a miner.

## Privacy

- No analytics, cookies, fingerprinting or third-party scripts in the arcade.
- Game progress and scores live in `localStorage` on the visitor's device.
- The Spotify badge exposes what the owner is listening to, by design. It uses
  two read-only scopes and cannot start, stop or modify playback.
- GitHub and Vercel may log requests (IP, user agent) according to their own
  policies; this project does not add logging beyond error categories.
- Issue games and their moves are public, like any GitHub issue.

---

## Supply chain

- **Zero runtime dependencies.** No npm install, no lockfile, no transitive
  packages, no CDN fonts or scripts. The arcade uses system monospace fonts.
- The only executable third parties are GitHub Actions from `actions/*`.
- Generated assets are produced by checked-in scripts, not by an image service.
- The Spotify function uses Node's built-in `fetch`/`Buffer` and no SDK.

This is the main reason the project is dependency-free: every removed package is
an attack surface that does not need a patch.

## Rotation runbook

### Spotify

1. In the Spotify dashboard, delete the app or rotate its secret.
2. Remove the app's access at <https://www.spotify.com/account/apps/>.
3. Run `node scripts/spotify-auth.mjs` again with the new client ID/secret.
4. Update the three Vercel environment variables and redeploy.
5. Confirm `/api/now-playing?format=json` returns `ok: true` and no token text.

### GitHub PAT

1. Revoke `PROFILE_TOKEN` at <https://github.com/settings/tokens>.
2. Create a replacement with `read:user` only.
3. Update the repository secret and run *Refresh profile assets*.

### Repository write access

1. If the Actions token or a collaborator is compromised, remove access, rotate
   credentials and review recent commits to `chess/games/` and `assets/`.
2. Game files are plain JSON; `git log -p` shows every change.

## Out of scope

- A compromised GitHub account or Vercel account with full access.
- A malicious browser extension reading the visitor's screen.
- Spotify account takeover.
- GitHub platform vulnerabilities.
- Availability of GitHub Pages, Actions, the Spotify API or Vercel.

Those are real risks, but they are not addressable from this repository. The
project's job is to avoid adding its own.
